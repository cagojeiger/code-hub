## 목표

**Hub-Spoke 아키텍처 도입**. Control Plane(Hub)을 OCI K8s에 배포하고, Agent(Spoke)는 NAT 뒤 어디서든 FRP 터널로 연결되는 구조로 전환한다.

```
┌──────────────────────────┐     ┌──────────────────────────┐
│  OCI K8s (Hub)           │     │  Agent Site (NAT 뒤)     │
│                          │     │                          │
│  ┌────────────────────┐  │     │  ┌──────────────────┐   │
│  │ Control Plane      │  │     │  │ Agent (FastAPI)   │   │
│  │ - API Server       │  │     │  │ - Docker Runtime  │   │
│  │ - Coordinator      │  │     │  │ - StorageManager  │   │
│  │ - Reverse Proxy    │  │     │  └──────────────────┘   │
│  └────────────────────┘  │     │                          │
│  PostgreSQL + Redis      │     │  MinIO + frpc            │
│  frps                    │◀════│  Container Runtime       │
└──────────────────────────┘ FRP └──────────────────────────┘
```

### v0.3.0 스코프

| 포함 | 제외 (v0.4.0+) |
|------|----------------|
| Hub-Spoke 구조 (CP/DP 분리) | 멀티 Agent 등록 시스템 |
| MinIO → Agent 이동 | K8s Runtime 구현 |
| FRP 터널 연동 | Agent Dashboard UI |
| CP Helm chart (OCI K8s 배포) | Agent-initiated HTTP 역전 |
| docker-compose 네트워크 분리 | |

### 핵심 제약

1. **Agent는 항상 NAT 뒤에 있다고 가정** — 모든 연결은 Agent→Hub 방향 (FRP)
2. **FRP를 기본 연결 수단으로 사용** — OCI K8s에 frps 이미 운영 중
3. **MinIO는 Agent(Data Plane) 쪽에 배치** — Hub에는 PostgreSQL + Redis + frps만
4. **기존 아키텍처 계약 보존** — Ordered SM, Level-Triggered, Single Writer 등 변경 없음

## 마일스톤

### Phase 0: CP/DP 네트워크 분리 — In Progress

docker-compose에서 CP와 DP의 네트워크를 물리적으로 분리하여, Hub-Spoke 전환의 기반을 만든다.

**Exit Criteria**: CP와 Agent가 서로의 인프라에 직접 접근 불가하고, Agent API를 통해서만 통신.

- [x] docker-compose 네트워크 분리 (`cp-net`, `dp-net`)
- [ ] CP에서 `S3_*` 환경변수 제거 (MinIO 직접 접근 불필요)
- [ ] CP에서 `DOCKER_HOST` 환경변수 제거 (Docker 직접 접근 불필요)
- [ ] CP의 `depends_on: agent` 제거 (네트워크 독립)
- [ ] `AGENT_ENDPOINT` 설정을 frps 프록시 URL로 전환 가능하도록 추상화
- [ ] 네트워크 격리 검증
  - CP → MinIO: 연결 실패 확인
  - CP → Docker Proxy: 연결 실패 확인
  - Agent → PostgreSQL: 연결 실패 확인
  - CP → Agent (정상 경로): 연결 성공 확인

**Notes**:


### Phase 1: FRP 터널 연동

Agent(frpc)가 Hub(frps)에 연결하여 CP→Agent 통신이 FRP 터널을 경유하도록 한다.

**Exit Criteria**: docker-compose 환경에서 CP↔Agent가 FRP 터널만으로 통신. 기존 observe/start/stop/archive 전체 동작.

- [ ] docker-compose에 frps/frpc 서비스 추가
- [ ] frps 설정 (인증 토큰, 포트)
- [ ] frpc 설정 (Agent API 터널, workspace 프록시 터널)
- [ ] `AGENT_ENDPOINT`를 frps 프록시 URL로 변경
- [ ] Workspace 프록시 라우팅을 frps vhost 경유로 변경
- [ ] E2E 테스트: 전체 lifecycle (create → start → stop → archive → restore → delete)

**Notes**:


### Phase 2: CP Helm Chart + OCI K8s 배포

Control Plane을 Helm chart로 패키징하고 OCI K8s 클러스터에 배포한다.

**Exit Criteria**: OCI K8s의 `codehub` namespace에 CP가 실행되고, 외부에서 접근 가능.

- [ ] Helm chart 구조 설계 (`charts/codehub-cp/`)
- [ ] CP Deployment (FastAPI + uvicorn)
- [ ] PostgreSQL StatefulSet (또는 외부 DB)
- [ ] Redis Deployment
- [ ] Ingress 설정 (외부 접근)
- [ ] ConfigMap / Secret 관리
- [ ] OCI K8s `codehub` namespace에 배포
- [ ] frps 서비스와 연동 확인 (기존 `frp` namespace)
- [ ] 외부에서 API 접근 확인

**Notes**:


### Phase 3: Agent + frpc 배포 검증

로컬/원격 Agent가 frpc를 통해 OCI Hub에 연결하는 E2E 시나리오를 검증한다.

**Exit Criteria**: NAT 뒤의 Agent가 OCI Hub에 FRP로 연결, 전체 workspace lifecycle 동작.

- [ ] Agent + frpc + MinIO docker-compose (Agent 측)
- [ ] frpc 설정: OCI frps 주소로 연결
- [ ] NAT 환경에서 연결 검증
- [ ] 전체 lifecycle E2E (create → start → code-server 접속 → stop → archive → restore)
- [ ] 장애 시나리오: frpc 재연결, Hub 재시작, Agent 재시작
